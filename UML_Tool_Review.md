# Враження від інструменту моделювання UML — PlantUML

Для всіх UML-діаграм цієї лабораторної (As-Is, To-Be та додаткові
завдання — `UML_As_Is/`, `UML_To_Be/`, `UML_Extra/`) використано
[PlantUML](https://plantuml.com/) — текстовий мова опису діаграм, що
рендериться в `.png`/`.svg` через Java-утиліту (`plantuml.jar`),
у парі з Graphviz `dot` або вбудованим pure-Java layout-движком
`smetana`.

## Чому обрано саме його

Головний критерій — **діаграми як код**. Кожна `.puml`-схема
зберігається поряд із джерельним кодом у тому ж репозиторії,
рендериться однією командою (`java -jar plantuml.jar file.puml`)
і легко інтегрується в CI/CD (наприклад, можна додати окрему job,
що при кожному `push` перевіряє рендер усіх діаграм без помилок —
аналогічно до вже наявного `docs.yml` для Doxygen). Це разюче
відрізняється від інструментів на кшталт StarUML чи Enterprise
Architect, де діаграма — це бінарний/XML-проєкт, який важко
переглядати в `git diff`, неможливо відрендерити з командного рядка
без GUI-сесії і складно автоматично тестувати на коректність.

## Плюси

- **Текстовий формат → дружній до Git.** Зміни в діаграмі видно як
  звичайний `diff` рядків, а не як "зображення змінилося, деталі
  невідомі". Злиття конфліктів так само просте, як для коду.
- **Швидкість ітерацій.** Додати новий клас чи зв'язок — це один
  рядок тексту; не потрібно вручну тягати фігури мишею й
  перевирівнювати layout після кожної зміни.
- **Широкий набір типів діаграм** — в одній мові й одному рушії
  доступні Use Case, Class, Sequence, Component, Activity, State,
  Object, Communication, Deployment та інші: саме це дозволило
  закрити вимогу "майже всі типи діаграм" без перемикання між
  різними програмами.
- **Безкоштовний і кросплатформний** — рендериться будь-де, де є
  Java; не вимагає ліцензії (на відміну від Enterprise Architect).
- **Інтеграція з документацією.** PlantUML-блоки можна вставляти
  прямо в Markdown/Doxygen-коментарі — діаграма генерується разом
  із рештою документації одним пайплайном.

## Мінуси

- **Автоматичний layout буває непередбачуваним.** Під час роботи
  кілька складних діаграм (`class_diagram`, `component_diagram`,
  `use_case_diagram`) стабільно "падали" з `EmptySvgException` при
  рендері через зовнішній Graphviz `dot` — довелося шукати причину
  й переходити на вбудований движок `!pragma layout smetana`
  (бачимо це й у вихідному коді самих `.puml`-файлів). Це типова
  "ціна" того, що розташування елементів не контролюється вручну.
- **Менш наочний для нетехнічної аудиторії.** Щоб побачити
  результат, треба відрендерити файл — на відміну від WYSIWYG-
  редакторів (StarUML, draw.io, Enterprise Architect), де картинка
  завжди "перед очима" і її одразу можна показати замовнику.
- **Тонке форматування — складніше.** Точне позиціювання нотаток,
  напрямки стрілок чи розміри блоків іноді доводиться "вгадувати"
  через директиви (`-down->`, `-right->`, `left to right direction`)
  методом проб і помилок, тоді як у графічному редакторі це
  робиться перетягуванням за секунди.
- **Повідомлення про синтаксичні помилки лаконічні.** Наприклад,
  помилка в розміщенні `note` (як у `UML_Extra/movie_plot/activity_diagram.puml`)
  повідомляється просто як "diagram contains errors" без точного
  пояснення причини — доводиться локалізувати проблему вручну.

## Підсумок

Для проєкту, де UML-діаграми супроводжують код у Git-репозиторії
(а не існують як окремий "паперовий" артефакт), PlantUML виявився
вдалим вибором: він перетворює моделювання на той самий процес, що
й написання коду — з контролем версій, відтворюваністю рендеру й
можливістю автоматизації через CI. Якби метою було створення
презентаційних матеріалів для нетехнічних стейкхолдерів або
складне ручне компонування великих enterprise-схем, інструмент
на кшталт Enterprise Architect чи StarUML, ймовірно, був би
зручнішим — але для навчального проєкту з акцентом на
відтворюваність і версійність PlantUML переміг за співвідношенням
"швидкість ітерації / контроль над процесом".
